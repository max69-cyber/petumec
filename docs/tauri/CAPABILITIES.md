# Capabilities

## Что это вообще такое

Capability-файл — это ACL (access control list) для одного или нескольких
окон. По умолчанию фронтенд (JS/Vue) **не может** вызвать ни одну
команду — ни встроенную Tauri-команду (типа "измени размер окна"), ни
свою `#[tauri::command]` — пока она явно не разрешена здесь. Это защита
от XSS: даже если во фронтенд попадёт вредоносный код, он физически не
дотянется до системных вызовов сверх того, что разрешено.

## Когда и как это применяется

Всё содержимое capabilities/-папки
зашивается в бинарник **на этапе компиляции** через
`tauri::generate_context!()` в `lib.rs`. В рантайме, когда фронтенд
вызывает `invoke(...)`, Tauri-ядро смотрит, из какого окна пришёл вызов,
сверяет с ACL для этого окна, и либо пропускает вызов к вашей команде,
либо тихо отклоняет — **без ошибки в консоли**, просто ничего не
происходит.

Tauri сам сканирует **всю папку** `capabilities/` и подхватывает
**все** `.json`-файлы из неё автоматически. Имя файла ни на что не
влияет. Можно сузить список явно через
`tauri.conf.json → app.security.capabilities`.

## Как файл привязывается к конкретному окну

Через поле `"windows"` — список glob-паттернов, которые сверяются с
**`label`** окна, который задаётся в `tauri.conf.json → app.windows[].label`, 
либо через `.label(...)` при создании окна в Rust).

`"identifier"` внутри capability-файла к окну отношения не имеет вообще —
это просто уникальное имя самой capability, нужное только чтобы:
- сослаться на неё по имени в `app.security.capabilities`, если решите
  сузить список
- отличать её от других capability-файлов в сообщениях об ошибках

## Что есть в permissions

### `core:default`

Автоматически включает 9 под-наборов, каждый под свой namespace:
`app:default`, `event:default`, `image:default`, `menu:default`,
`path:default`, `resources:default`, `tray:default`, `webview:default`,
`window:default`.

`core:window:default` даёт только **безопасные, read-only** вещи —
узнать размер/позицию/масштаб окна, спросить `is_fullscreen` /
`is_minimized` / `is_focused` / `is_visible` и т.п., получить список
мониторов, позицию курсора, тему. Ничего, что реально **меняет**
состояние окна, в default не входит — это осознанно, каждую такую
команду нужно разрешать явно по отдельности:
`allow-close`, `allow-minimize`, `allow-maximize`/`unmaximize`,
`allow-hide`/`show`, `allow-center`, `allow-set-position`,
`allow-set-title`, `allow-set-icon`, `allow-set-theme`,
`allow-set-focus`, `allow-set-always-on-top`,
`allow-start-dragging`, `allow-set-size`.

### Остальные namespace'ы под `core:`

- **`app`** — жизненный цикл приложения (например `app_hide`)
- **`event`** — emit/listen событий между фронтом и Rust
- **`image`** — работа с изображениями
- **`menu`** — создание/управление меню
- **`path`** — резолв путей файловой системы
- **`resources`** — управление ресурсами/их очисткой
- **`tray`** — иконка в трее/менюбаре
- **`webview`** — управление самим вебвью (не окном целиком, а именно
  рендер-слоем внутри него)

### Плагины (каждый со своим `<plugin>:default` + точечные разрешения)

- **`opener`** — `default` открывает `mailto:`/`tel:`/`http(s)://`
  через дефолтное приложение системы + показ файла в Finder
  (`reveal-item-in-dir`). Отдельно есть `allow-open-path` (открыть файл
  по пути конкретным приложением) и `allow-open-url` (произвольные
  URL/схемы, не только стандартные) — оба требуют glob-паттерн, какие
  именно пути/URL разрешены.
- **`fs`** — доступ к файловой системе (чтение/запись/список файлов),
  с обязательным scope — какие именно пути разрешены
- **`dialog`** — системные диалоги выбора файла/папки, message box
- **`notification`** — системные уведомления
- **`shell`** — запуск внешних процессов/команд
- **`clipboard-manager`** — чтение/запись буфера обмена
- **`global-shortcut`** — глобальные хоткеи, работают даже когда
  приложение не в фокусе
- **`store`** — простое персистентное key-value хранилище на диске
- **`autostart`** — запуск приложения при логине в систему

Каждый плагин нужно сначала подключить как Rust-зависимость и
`.plugin(...)` в `lib.rs`, только после этого его permissions вообще
имеют смысл упоминать в capability-файле.
